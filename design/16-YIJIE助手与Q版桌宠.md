## 一、三点菜单看不清：修了两次才对

### 第一次修（错了）

我以为是主题没指定 popup 颜色，于是在 `themes.xml` 里加了
`popupMenuStyle` / `android:itemTextAppearance` / `alertDialogTheme`，
还写了个深色背景 drawable。

**结果更糟**：变成白底白字，比原来还看不见。

**原因**：AppCompat 的 `PopupMenu` **不读主题里的 `android:popupBackground`**。
它由内部 `MenuPopupHelper` 自己创建背景，主题那一项对它无效。

### 第二次修（也在试错）

改用反射：`mPopup` → `getPopup()` → `setBackgroundDrawable()`。

**失败**：

```
W MainActivity: popup bg: com.android.internal.view.menu.MenuPopupHelper.getPopup []
```

`getPopup` 是隐藏方法，不同 ROM 的签名不一样，反射拿不到。

### 第三次修（成了）

**放弃 `PopupMenu`，自己搭一个列表对话框。**

```java
android.widget.LinearLayout box = new LinearLayout(this);
box.setBackgroundColor(0xFF1E1633);       // 深紫底，写死
// 每一项：
tv.setTextColor(0xFFF4F2FF);              // 浅色文字，写死
tv.setTextSize(16);
// 按下时给背景反馈
```

好处：

- **颜色 100% 可控**，不经过任何主题/系统行为
- 不依赖反射，不会因 ROM 差异失效
- 顺手加了分隔线、按下的高亮反馈、圆角

**实测**：深紫底 + 浅色文字，10 个入口清晰可读。

> 教训：涉及系统默认外观的东西，如果两次改主题都无效，
> 就该**停止调主题，自己画**。PopupMenu 的背景属于"系统管得比你多"的典型。

## 二、桌宠改用 Q 版形象

你说"太丑"是对的 —— 之前那颗手绘球跟角色没有任何关系。

### 现在的做法

用 `PetAvatar` 调 Pollinations 生成**该角色的 Q 版形象**，提示词写死风格：

```
chibi style, super deformed, 3 heads tall, big head,
cute anime character portrait, {角色名}, {性格}, {标签},
soft pastel colors, kawaii, simple flat background, centered
```

关键风格词是 `chibi` + `super deformed` + `3 heads tall` —— 不写这些，
模型会给出正常比例的人物，做桌宠太大太重。

### 绘制（`PetAvatarRenderer`）

三个让图片看起来"活的"的细节：

1. **圆形裁切**：悬浮在桌面上不能有方边。
   用 `BitmapShader` + `drawCircle`，不是贴一张方图。
2. **弹跳形变**：落地压扁到 80%、横向变宽到 120%（保持体积感）；
   被拖拽时纵向拉长到 110%（像被拎起来）。
   用 `Matrix` 缩放 shader，不每帧 `createBitmap`。
3. **底部接触阴影**：贴地时浓，飞起时淡。
   这是"她在桌面上"而不是"贴在屏幕上"的关键。

### 缓存与兜底

- 生成一次后存 `files/pet/{cardId}_q.png`，之后直接读
- **首次还没有 Q 版图时，用角色头像裁圆兜底** —— 不会出现"桌宠是空的"
- 长按菜单里有「重新生成 Q 版形象」

球体尺寸从 68dp 加大到 **92dp**，Q 版图才看得清脸。

## 三、YIJIE 助手 + 技能插件

### 名字与人格

你要求「不是绝对没有人格」，改名 **YIJIE**。

新版 prompt 的定位是：**有稳定的性格和工作方式，但不扮演、不卖萌、不谈感情**。

```
【你是谁】你不是角色扮演出来的形象，就是一个干活的人。
         你有自己的判断和偏好，但不会把它强加给对方。
【你怎么说话】直接、简洁、有判断、不确定就说不确定。
             偶尔可以用一句简短评价，但不要滥。
【你不做什么】不扮演、不卖萌、不撒娇、不谈感情、不说免责声明。
```

之前那版是「你没有名字、没有性别、没有性格、没有情绪」——
那是**工具**，不是**助手**。现在这版是个人，但不演戏。

### 6 个技能插件

技能的实现方式值得说明：**不是 function calling，而是"提示词 + 输出规范"的组合。**

为什么不做真正的工具调用：
- 需要模型支持，并且客户端要解析流式 JSON 分片
- 本地 7B 模型经常吐不出合法 JSON，**反而更不可靠**
- 而"给一套明确输出规范 + 把结果落盘"能达到同样效果，且任何模型都稳定

| 技能 | 产物 |
|---|---|
| 📄 **写文档** | **完整 Markdown → 自动存到「我的文档」** |
| 💻 写代码 | 可运行代码 + 关键点说明 |
| 📝 总结 | 一句话结论 + 3~7 条要点 |
| 🌐 翻译 | 保留原文结构，专有名词双语标注 |
| 📋 做计划 | 有序步骤 + 完成标志 + 风险点 |
| 🔍 分析 | 复述问题 + 关键因素 + 明确判断 |

### 写文档的落盘链路

这是"最起码可以写文档"的具体实现：

```
选了「写文档」技能
   ↓
回复内容自动检测（looksLikeDocument：有 # 标题 + ≥2 个 ## 小节 + >300 字）
   ↓
存到 files/docs/{标题}_{时间戳}.md
   ↓
消息末尾追加「📄 已保存到「我的文档」：xxx.md」
   ↓
菜单 →「我的文档」可查看 / 导出
```

导出会写到 `Android/data/com.echoflow.chat/files/docs/`，
用文件管理器能找到，也可以直接复制全文。

### 文档检测的取舍

用启发式规则（标题 + 小节数 + 长度）判断"这算不算文档"，
而不是让模型输出特殊标记。理由：**多一个标记就多一个模型可能不遵守的约定**。
启发式在真实场景下足够准，误判的代价也只是多存一个文件。

  我只确认了代码路径与兜底逻辑。

这两条是"接通了但没实测"，不是"做完了"。

### 仍然没做到的

- **桌宠只有一只**，且重启后不自动恢复。
