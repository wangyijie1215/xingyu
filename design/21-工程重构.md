# 工程重构

> 对应 `dist/EchoFlow-v3.6-工程重构.apk`（8.03 MB）

这一轮没有新功能，只做三件"地基"的事，外加 GitHub 发布准备。

为什么要停下来做这个：这个项目是**一天里堆出来的**，98 个类、2 万行。
功能加得越快，结构越跟不上——具体表现是**我每加一个渠道就要重写一遍网络代码**
（今天已经在同一个坑里摔了两次），**每改一次视觉就要动九个文件**。
继续堆功能的话成本只会越来越高。

---

## 一、`Http.java`：统一网络层

### 问题

项目里有 **16 处手写 `HttpURLConnection`**。后果很具体：

我在接入 ComfyUI 时踩到一个坑 —— Android 对较大的 POST 会自动加
`Expect: 100-continue`，等服务端先回 `100 Continue` 再发正文。
有些服务端不回，**请求就永远卡在"发送中"，而且 `setReadTimeout` 管不到这一段**。

表现是：GET 正常、POST 卡死、不报错、不超时。我花了好几轮才定位。

修好之后，转头写 CosyVoice 渠道时，**在 `TtsProvider` 里又原样写了一遍**。

### 做法

抽一个 `Http` 类，把那两行关键设置封在里面：

```java
conn.setRequestProperty("Expect", "");              // 坑 1
conn.setFixedLengthStreamingMode(payload.length);   // 坑 2
```

顺手统一了：
- 超时策略（连接 10s / 读取 120s）
- 错误信息截断（避免把整页 HTML 塞进 UI）
- 二进制响应不被误当字符串处理（音频会坏）

`TtsProvider` 和 `ImageProvider` 都改成了调用它，各删掉约 40 行重复代码。

### 顺手删掉的死代码

`ImageGen.java`（159 行）是接入多渠道**之前**的旧实现，只支持 Pollinations。
`PetAvatar` 还在用它。改指向 `ImageProvider` 之后它就没人调了，删掉。

副作用是好的：**桌宠的 Q 版生成也能用上本地 ComfyUI 了**。

## 二、`EfActivity.java`：页面基类

### 问题

- `dp(int)` 这个方法在 **13 个文件里各写了一遍**
- 状态栏注入代码手写了 **9 遍**
- `getSharedPreferences` 出现 **18 次**

改一个通用行为要动十几个文件。上一轮换设计色板时，我只能靠全项目 grep
去找散落的硬编码色值——就是因为没有这层基类。

### 做法

`EfActivity` 只收拢最重复的东西：

| 方法 | 作用 |
|---|---|
| `dp()` | 尺寸换算 |
| `contentColumn()` | 带统一内边距和底色的内容容器 |
| `wrapScroll()` | 包一层滚动容器 |
| `attachStatusBar()` | 挂自绘状态栏 |
| `addTitle()` / `addSection()` / `hint()` | 三种固定排版样式 |
| `settingRow()` | 「标签 —— 值 ›」这种设置行 |

`wrapScroll()` 里有个容易漏的点写进了注释：**`ScrollView` 自己也要设底色**，
否则内容不满一屏时，下方露出的是它的背景（主题默认白）。
这个坑在桌宠设置页真的出过一次。

## 三、`PhoneStore`：JSONL 增量写

### 问题

```java
// 旧实现：每次保存，把整个对话重新序列化再整文件覆盖
for (Message m : messages) { arr.put(...); }
fw.write(arr.toString());
```

聊到 2000 条时，**每发一条新消息都要重写 2000 条**。这是 O(n)。

### 做法

改成 **JSONL**（一行一条消息）：

```
{"role":"assistant","content":"今天新到的一批里，有本你可能会喜欢的。\n什么时候过来坐坐。"}
{"role":"user","content":"在的"}
{"role":"assistant","content":"嗯。"}
```

追加是 O(1)，只往文件末尾写一行。

**兼容老数据**：老格式（整个文件是一个 JSON 数组）仍然能读，
读到之后下次写入自动迁移成 JSONL。已经聊了几百条的存档不会丢。

还有个额外好处：**单行损坏不影响其余**。
原来的 JSON 数组是一体的，任何一处破损整个文件都读不出来；
JSONL 里坏了一行只丢那一行。

### 验证

实测发一条消息，文件从 120 字节增到 208 字节，
内容正确多出 `user` + `assistant` 两行：

```
{"role":"assistant","content":"今天新到的一批里，有本你可能会喜欢的。..."}
{"role":"user","content":"hellotest123test123"}
{"role":"assistant","content":"嗯。"}
```

## 四、GitHub 发布准备

### 🔴 发现的问题

**签名密钥库的密码硬编码在 `build.gradle` 里**，而这个文件是要进 git 的：

```gradle
storeFile file('../echoflow-release.jks')
storePassword 'echoflow'      // ← 等于公开
keyPassword 'echoflow'
```

而且 `echoflow-release.jks` 本身也在仓库里。**任何人拿到它就能签出
冒充你的更新包**——这是要命的。

### 做法

密码抽到 `keystore.properties`（已在 `.gitignore` 里），
另附一份 `keystore.properties.example` 供他人参考：

```gradle
def keystoreFile = rootProject.file('keystore.properties')
def hasKeystore = keystoreFile.exists()     // 没有时不签名，debug 构建照常
```

密钥库本体移出仓库，留在 `_echoflow-keys/`。

顺便清了：
- 21 个编译日志（`be*.txt`、`p*.txt`……我调试时 generate 的）
- 4 个源码备份目录（`_backup-*`，有 git 之后就不需要了）
- `apk/`（854 个文件的解包产物，占仓库 65%）

### 截图压缩

`shots-android/` 有 90 张 1080×2400 的 PNG，共 42 MB。
转成 JPEG（q=4）后 **12.8 MB**——看截图验证效果完全够用。

仓库最终 **30.8 MB / 463 个文件**。

### 已推送前检查

| 检查项 | 结果 |
|---|---|
| API key、签名密码 | ✅ 全库扫描无 |
| `.jks` / `keystore.properties` | ✅ 不在索引里 |
| 编译日志、反编译产物 | ✅ 已排除 |
| `.gitignore` 覆盖 | ✅ 逐项验证 |

此外把 `versionCode` 从 `2` 补到 `6`、`versionName` 从 `2.0.0-神社`
更新到 `3.6.0`——这两个值之前一直忘了跟着版本走。

## 六、还没做到的

这一轮只治了地基，**上一轮列的体验项一个都没做**：

- **音色克隆** —— 百炼支持，能让每个角色有专属声音（最值得做的下一步）
- **情绪联动 TTS** —— CosyVoice 有 `emotion` 参数，`EmotionState.mood` 是现成的
- **语音识别（STT）** —— 现在打电话仍是单向的
- **`EfActivity` 只收拢了工具栏方法** —— 29 个 Activity 还没有真正继承它改造，
  只是新页面可以直接用。老页面逐个迁移是后续工作
- **`PhoneAppActivity` 986 行** —— 里面塞了五个 app，该拆

## 七、下一步该推 GitHub 了

仓库已经干净，但**推送还需要你**：

1. 在 GitHub 建一个空仓库（**不要**勾选 README/gitignore，会和本地的冲突）
2. 把地址给我，或者你自己执行：

```bash
cd _echoflow
git remote add origin <你的仓库地址>
git push -u origin main
```

推送前建议再确认一次远程仓库是 **private**——虽然扫描过了，
但这是个包含大量个人向内容的项目，先私有不亏。
