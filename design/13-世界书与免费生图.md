## 一、生图：接了，是免费的，不用 key

### 选型

用的是 **Pollinations**：把提示词直接写在 URL 里，返回一张 JPEG。

```
https://image.pollinations.ai/prompt/{提示词}?width=&height=&seed=&nologo=true&model=sana
```

**为什么是它**（不是随手挑的，是实测对比后的结论）：

| 要求 | Pollinations 是否满足 |
|---|---|
| 不要 API Key | ✅ URL 直出，无需注册 |
| 不要钱 | ✅ 公共免费服务 |
| 能出图 | ✅ 实测 HTTP 200，返回真 JPEG |
| **同 seed 同图** | ✅ **实测两次请求 MD5 完全一致** |
| 手机端好接 | ✅ 就是一个 GET 请求 |

最后一条特别关键：**如果同一提示词每次出不同的图，就没法缓存** ——
每次进页面都重新生成，又慢又费流量，而且角色的脸每次都变。
实测确认同 seed 稳定之后，缓存策略才成立。

### 三种生成方向

| 方向 | 提示词构成 | 缓存 key |
|---|---|---|
| **角色立绘** | 角色名 + 性格 + 二次元风格词 | `portrait_{cardId}` |
| **世界场景图** | 当前世界书的名字 + 描述，无人物 | `scene_{lorebookId}` |
| **她此刻的自拍** | 角色名 + 当前情绪 + 当前日程 + 所在世界 | `selfie_{cardId}_{日期}_{日程}` |

自拍的 key 里带了日期和日程，所以**她的状态变了，图就会换**；
但同一天同一状态下，图是稳定的。

### 实测数据

```
首次生成（角色立绘）：10 秒完成，42 KB
缓存命中：秒开，不再请求网络
清空缓存：可用，界面显示占用 KB
```

### 画风的坑

第一版生成出来是**真人照片质感**——写实、有皮肤纹理，和角色的二次元人设完全不搭。

**修复**：把风格词写死在前后缀里，不让模型自由发挥：

```java
private static final String STYLE_PRE =
        "anime style, 2D illustration, cel shading, key visual, ";
private static final String STYLE_POST =
        ", masterpiece, best quality, detailed, vibrant colors, "
        + "japanese animation art, trending on pixiv";
```

改完之后是明显的赛璐璐动画风。

### 已知限制（界面上有「说明」按钮写了）

- 公共服务，高峰期可能慢（实测本次 10 秒，但会波动）
- 画风偏半写实，靠风格词压成二次元，但不是专门的动漫模型
- 没有任何可用性承诺，失败时界面会明确报错而不是一直转圈
- 生成缓存存在 `files/genimg/`，可在生图页一键清空

## 二、世界书

### 是什么

**按关键词触发的小设定**。不是把一堆设定永远塞进 Prompt，而是：
聊天里说到相关词，对应条目才注入；没说到就不占上下文。

与角色卡的分工：

- 角色卡写「**她是谁**」（长期不变的人设）
- 世界书写「**她所在的世界是什么样的**」（可切换、按需注入）

### 数据模型

```java
class Lorebook {
    String id, name, description;
    boolean global;              // 全局世界书对所有角色生效
    List<Entry> entries;
}

class Entry {
    List<String> keys;   // 触发词，命中任一即注入
    String content;      // 注入的正文
    boolean constant;    // 常驻（不靠关键词，永远注入）
    int order;           // 越大越优先
}
```

### 触发逻辑

```java
list.triggered(recentMessages, scanDepth=8, maxEntries=6)
```

- 扫描最近 8 条消息
- `constant` 条目永远注入
- 其余条目：文本里出现任一 key（大小写不敏感）就注入
- 按 `order` 降序，最多 6 条

`content` 为空、`keys` 全空的条目会被跳过 —— 避免把空设定注入进去。

### 内置 4 本

风格刻意拉开，用来演示「同一个角色可以活在不同世界里」：

| 世界书 | 风格 | 今天的天气 | 默认绑定 |
|---|---|---|---|
| **雨夜都市** | 现代都市，多雨，霓虹与末班电车 | 阴 15~21℃ | 月铃、艾莲 |
| **银月骑士团** | 低魔奇幻，边境城邦与旧誓约 | 初雪 -2~4℃ | 爱丽丝 |
| **星见天文社** | 近未来校园科幻，山顶观测站 | 晴 10~18℃ | 白夜 |
| **旧城机械铺** | 当代日常，修理铺与街坊 | 雷雨 19~25℃ | 洛可、凛 |

每本 6~7 条设定。以「雨夜都市」为例：

```
[常驻] 世界基调     故事发生在一座常年多雨的现代都市…
[常驻] 天气体系     这个世界的天气自成体系…
[老城区/河北/巷子]  老城区在河北岸，楼都不高，六七层…
[电车/末班/车站]    有一条环线电车绕城一圈，末班是 23:40…
[便利店/关东煮]     街角有一家 24 小时便利店…
[雨/下雨/伞]        这座城市的雨有自己的脾气：不大，但会下很久…
[钟楼/报时]         广场上有一座停在 3:47 的旧钟楼…
```

### 注入位置

世界书段落接在手机模式规则的**后面**、日程的后面：

```
[角色卡 system prompt]
  + 【当前场景：手机聊天】…（只说话，不要动作）
  + 【你此刻的日程】…
  + 【世界设定 · 雨夜都市】…
```

这样优先级是正确的：角色人设 > 输出格式约束 > 当下情境 > 世界背景。

## 三、天气接上世界书了

这是加世界书**最直接的收益**。

以前天气页写的是「未接入」——因为手机所在地的天气和角色没关系，
而硬编一个假温度更糟。现在不同了：**每个世界有自己的天气体系**。

实测结果：

```
「雨夜都市」今天
阴
15~21℃
云压得很低，天色比平时暗得早。

艾莲    这种天最适合待在屋里。
爱丽丝  下雪了。营地里的人都在看。   ← 她在银月骑士团
月铃    这种天最适合待在屋里。
洛可    这种天最适合拆东西。         ← 他在旧城机械铺（雷雨）
白夜    云量很低，是难得的天。       ← 他在星见天文社（晴）
凛      打雷了，屋顶响得要命。       ← 旧城机械铺
```

**注意每个角色说的是自己那个世界的天气** —— 爱丽丝说下雪，白夜说云少，
凛说打雷。这不是随机挑句子，是各自查了各自世界的天气表。

天气的确定性算法：

```java
long h = FNV1a(lorebookId + "|" + date);
Weather w = weathers[index = h % weathers.length];
```

同一天 + 同一本世界书 = 同一个天气（刷新不变）；
不同世界书同一天 = 不同的天。

## 六、这轮踩的坑（工具链）

### javac 默认 GBK

用 `javac` 编译含中文的辅助工具时报：

```
错误: 编码 GBK 的不可映射字符 (0xA8)
```

**修复**：`javac -encoding UTF-8`，运行用 `-Dfile.encoding=UTF-8`。

### Java 类有 package 就不能用裸类名跑

`ReplaceWeather.java` 声明了 `package com.echoflow.chat;`，
`java -cp _cls ReplaceWeather` 会报 `ClassNotFoundException`。

**正确**：`java -cp _cls com.echoflow.chat.ReplaceWeather`

### 长中文文本替换用 Java 而不是 PowerShell

改 `PhoneAppActivity` 的整个 `weatherBody()` 方法（约 100 行含大量中文）时，
PowerShell 的字符串替换反复出问题。最后写了个 30 行的 Java 程序做**按行区间替换**：

```
java com.echoflow.chat.ReplaceWeather <源文件> <新方法体文件>
```

定位 `private View weatherBody()` 和 `private View notesBody()` 两个锚点，
替换中间整段。一次成功。

**结论**：涉及大段中文的源码改造，用能精确控制字节的工具（Java/Python），
别用 PowerShell 的 `-replace`。

### 提示词里的中文名会撑爆 URL

角色名和性格描述是中文，直接 URL 编码后长度可能过千。
`ImageGen` 里做了截断（80 字符上限）+ 去换行，避免 URL 过长被拒。
